# v3.1 実装のセキュリティ所見（自己レビュー）

対象: `feature/v3.1` の `contracts/ShirushiCoin.sol`
方法: コード読解 ＋ Hardhat（solc 0.8.36 / evmVersion prague）での再現テスト。
以下の「確認済み」はすべて実際にテストで再現した挙動で、推測ではない。

機能対応表どおりに実装した結果として**残っている**穴が中心。

**裁定結果（2026-09-13）**: S-1 と S-2 は **今回は修正せず所見として残す**（機能対応表を正本と
するため）。第三者監査でも同じ指摘が出る前提で、監査前に別途裁定する。S-5 は**運用で対応**
（デプロイ直後に `registerExchange(poolAccount)` を実行。手順は `v3.1-changes.md` に記載）。
したがって現時点でコードに変更は入れていない。

---

## S-1 [Critical] `setMiningReward` ＋ `setPoolAccount` ＋ `mine` で adminMint が再構築できる

**確認済み**: `MINING_ADMIN_ROLE` と `MINER_ROLE` の 2 鍵で、
**1 トランザクションで残枠 87,732,080 SISC を任意のアドレスへ発行**できた。

```
setMiningReward(2030, 87_732_080e18)   // MINING_ADMIN。reward に上限が無い
setPoolAccount(attacker)               // MINING_ADMIN。受取先も任意
mine(2030)                             // MINER。cap まで mint
```

さらに `DEFAULT_ADMIN_ROLE` は他ロールを自分に付与できるため、**admin 鍵 1 本でも同じことができる**
（S-3 参照。テストで再現済み）。

**何と矛盾するか**

- 機能対応表「adminMint（裁量ミント）→ 削除／発行は mine() のみ」— 関数名は消えたが、
  同じ結果（任意額・任意宛先の発行）に到達する経路が残っている
- 提案書 §5.1「残高に触れる権限をゼロにする」、§5.6「他人の残高を増やせず・減らせず」
- 提案書 §5.5「実効的な発行上限 ≈ 237M」— この実装では**実効上限は cap の 300M**
- スキャナ観点でも `is_mintable` の説明が「固定スケジュールのみ」では成り立たない

**選択肢**

| | 内容 | 機能対応表との関係 |
|---|---|---|
| a | `setMiningReward` を「減額のみ・将来年のみ」に制限（`reward < 現在値` かつ `year > 現在年`）＋ `MiningRewardChanged` は既に実装済み | 行は維持したまま条件を追加（提案書 F-07）。**推奨** |
| b | 報酬表を `pure` 関数化し `setMiningReward` を削除 | 機能対応表「維持・変更」から「削除」へ移る＝要裁定（提案書 §5.2 の案） |
| c | 期間ごとの発行上限 `mintedInPeriod[年] <= 当年報酬 × 365` を機械強制 | 新規ガードの追加（提案書 F-23）。a と併用可 |

a だけでも「発行額を増やす方向の変更が不可能」になり、S-2 と併せて実効上限を ≈237M と
言い切れるようになる。

## S-2 [High] `mine(year)` の `year` は呼び出し側指定のまま — 逓減スケジュールがオンチェーンで強制されていない

**確認済み**: 2026 年に `mine(2022)` を 23 時間ごとに繰り返し、2022 年レート（10,000）で
発行し続けられた（3 回 = 30,000 SISC）。同一年の再採掘に回数制限も無い。

- MINER のホットキー（EC2）が漏れた場合の被害上限は **cap までの残枠全部**（10,000/23h のペース）
- 機能対応表は「mine / 報酬表 / poolAccount は維持」なのでこれは仕様通りだが、
  提案書 F-08 の指摘（監査・スキャナが問題視）はそのまま残る

**選択肢**: `year` 引数を廃止し `block.timestamp` から UTC 年を導出（提案書 F-08・§5.8 のスケッチ）。
これは機能対応表の「維持」を「変更」に変える裁定になる。暫定策として、MINER を Safe にする／
被害上限を S-1 の c（年間上限）で有界化する方法もある。

## S-3 [High] DEFAULT_ADMIN は固定だが、全ロールを自分に付与できる — かつ鍵の回転ができない

**確認済み**:

- `admin` は FREEZER / WHITELIST / MINING_ADMIN / MINER / RECORDER を自分に `grantRole` できた
  → ロール分離（「最上位権限から分離」）は **admin 鍵の強度以下**にしかならない
- `grantRole(DEFAULT_ADMIN_ROLE, ...)` / `revokeRole` / `renounceRole` はすべて `AdminIsFixed` で revert
  → **admin 鍵が漏れても永久に剥奪できない**。復旧手段は再デプロイ＋移行のみ

v3 では admin を別アドレスへ移せたので、「固定」はこの一点だけリスクを増やしている
（取引所要求 1 の「移行可能な admin」への懸念は消えるが、鍵の回転手段も消える）。

**結論（デプロイ制約）**: `roleHolders.admin` は **EOA にしてはいけない**。署名者を交換できる
Safe（提案書の推奨は Timelock 48h ＋ Safe 3-of-5）を入れること。アドレスは後から変更できないため、
デプロイ前に確定が必要。同様に、日常運用ロールは admin と別アドレス・別端末にする意味が
（S-3 の性質上）「admin 鍵が無事な限り」に限られることを対外説明でも曖昧にしない。

## S-4 [Medium] 凍結中も `approve` / `permit` が通る — 解凍と同時に引き抜かれる

**確認済み**: 凍結中の保有者が `permit` に署名 → allowance が立つ → `unfreeze` 後に
`transferFrom` で全額流出（同一ブロックでも可）。

`ERC20Restricted` は設計上 approve を制限しない（上流のコメントどおり）。v3.0 の NatSpec は
「凍結中は approve も制限される」と書いていたが実装はしていなかったため、v3.1 では
NatSpec を実装に合わせて修正済み（＝虚偽記載は解消）。ただしリスク自体は残る。

**対処**: 提案書 F-25 のとおり「unfreeze 前に対象アドレスの `Approval` ログを全件確認する」を
解凍手順書の必須ゲートにする。コードで塞ぐ場合は `_approve` の override（凍結中の増額のみ拒否）。

## S-5 [Medium] `poolAccount` を凍結すると採掘が止まる（自傷 DoS）

**確認済み**:

- `freeze(poolAccount)` → `mine()` が `ERC20UserRestricted` で revert（unfreeze すれば復帰）
- `setPoolAccount` に制限状態のチェックが無いため、**凍結中のアドレスを受取先に設定**して
  採掘を止めることもできた

**対処（コード変更なしで可能）**: `registerExchange(poolAccount)` で poolAccount をホワイトリスト
登録しておけば、独自ガード（ALLOWED → BLOCKED 禁止）により**構造的に凍結不能**になる。
テストで確認済み。コードで塞ぐなら `setPoolAccount` に `getRestriction(account) != BLOCKED` を追加。

---

## S-6 [解消] 取引所アドレスの保護が `WHITELIST_ROLE` 鍵 1 本で即時に外せた

**2026-09-16 のホワイトリスト追記専用化で構造的に解消。** `unregisterExchange` を削除し、
`_setRestriction` で `ALLOWED` を終端状態にしたため、登録済みアドレスの保護を外す経路が
コード上に存在しない。`DEFAULT_ADMIN_ROLE` が `FREEZER_ROLE` と `WHITELIST_ROLE` を自分に
付与しても `freeze` / `unfreeze` の双方が revert することをテストで確認済み。

ただし**不可逆性そのものが新しいリスク**として残る。

- 誤登録の訂正手段が再デプロイしか無い
- `WHITELIST_ROLE` 鍵が漏れた場合、任意アドレスに**恒久的な**凍結免除を与えられる
  （件数・レート制限は未実装。提案書 §5.4 のローリング 7 日 200 件は引き続き未実装）

**対処**: `WHITELIST_ROLE` を Safe にし、登録前のアドレス確認手順を書面化する。取引所への
説明は「登録後は解除できない」に変わるため、S-7 と併せて合意内容を更新すること。

## S-7 [Low] 取引所のユーザー毎入金アドレスは事前登録できない

動的生成されるため、登録対象はホット・コールド・出金元・スイープ先に限られる。
LBank 要求 3 を「全入出金アドレスの除外」と読むと**技術的に充足不能**。提案書 §5.4 と同じ結論で、
実装側で解決できる問題ではないので書面で合意する。

## S-8 [Low] 凍結に期限が無い（機能対応表どおり）

FREEZER 鍵を失うと恒久凍結になる。`unfreeze` は FREEZER 専用で、admin は自分に FREEZER を
付与すれば解除できる（＝ admin 鍵が最後の砦）。提案書の自動失効（7 日／30 日）は未実装。
また freeze はメモリプールで観測できるため、対象は先回りして送金できる（v3.0 と同じ）。

## S-9 [Low] v3.0 との ABI 互換性が切れる箇所

- `initialSupply()` は廃止（`genesisSupply()` に改名）
- `maxSupply()` は `cap()` のエイリアスとして残置（互換）
- `POOLER_ROLE()` / `PAUSER_ROLE()` / `pause()` / `adminMint()` 等は消滅
- `unregisterExchange()` は消滅（ホワイトリストの追記専用化。S-6）
- `ExchangeRegistered` のシグネチャが `(address indexed, bool)` から
  `(address indexed, uint256 index)` に変更（解除が無くなり bool が無意味になったため）
- ロール定数は `private` → `public` に変更（ABI に出る）

`scripts/` と運用ツール（readcheck の immutable マスク等）は要修正。`artifacts/` は v3.0 の
Remix 出力のまま更新していない。

## S-10 [Low] イベントが二重に出る

`freeze` は `AccountFrozen` と `UserRestrictionsUpdated`、`registerExchange` は
`ExchangeRegistered` と `UserRestrictionsUpdated` の 2 本を出す（`ERC20Restricted` 由来）。
監視側で二重カウントしないこと。`registerExchange` の 2 本はいずれも 1 アドレスにつき最大 1 回で、
解除側のイベントは存在しない。`genesisHolders` の重複アドレスも検証していない（合計額は正しい）。

## 良くなった点（監査で加点になる）

- **バーン経路が 1 つも無い**ため、`ERC20Capped` の cap が実質的に**累積発行上限**として機能する
  （`transfer(0x0)` も `ERC20InvalidReceiver` で revert。提案書 F-16 の「burn → re-mint で上限を
  無効化」は構造的に解消）
- `multiTransfer` は permissionless だが、他人の残高には触れない（`ERC20InsufficientBalance` で
  revert することを確認済み）。権限一覧を 1 つ減らせる
- ホワイトリストは**追記専用**で、登録済み取引所アドレスは `DEFAULT_ADMIN_ROLE` を含むどの鍵でも
  凍結・解除できない（`unfreeze` 経由の迂回路も塞いだ）。保護が鍵の管理状態に依存しなくなった
- 登録簿が `getRegisteredExchanges()` で全件列挙でき、取引所側が自分のアドレスの登録状態を
  第三者に依存せず検証できる
- ロール保持者が `getRoleMembers` でオンチェーン列挙可能、凍結・登録状態も view で検証可能
