# v3.1 実装のセキュリティ所見（自己レビュー）

対象: `feature/v3.1` の `contracts/ShirushiCoin.sol`
方法: コード読解 ＋ Hardhat（solc 0.8.36 / evmVersion prague）での再現テスト。
以下の「確認済み」はすべて実際にテストで再現した挙動で、推測ではない。

機能対応表どおりに実装した結果として**残っている**穴が中心。

**裁定結果（2026-09-13）**: S-1 と S-2 は **今回は修正せず所見として残す**（機能対応表を正本と
するため）。第三者監査でも同じ指摘が出る前提で、監査前に別途裁定する。S-5 は**運用で対応**
（当初）。**その後 2026-09-17 の全体レビューで、S-4 の裏返しにあたる「凍結した spender による
引き抜き」を `_spendAllowance` の override で塞いだ。** S-5 は一度コードで塞いだが、発行先を
永久に凍結不能にする副作用が重く撤回し、受容に戻した（S-5 参照）。S-1 / S-2 は引き続き未修正。

---

## S-1 [Critical] `setMiningReward` ＋ `setPoolAccount` ＋ `mine` で adminMint が再構築できる

**確認済み**: `MINING_ADMIN_ROLE` と `MINER_ROLE` の 2 鍵で、
**1 トランザクションで残枠 87,732,080 SISC を任意のアドレスへ発行**できた。

```
setMiningReward(2030, 87_732_080e18)   // MINING_ADMIN。reward に上限が無い
setPoolAccount(attacker)               // MINING_ADMIN。受取先も任意
mine(2030)                             // MINER。cap まで mint
```

さらに `DEFAULT_ADMIN_ROLE` は他ロールを自分に付与できるため、**admin 鍵 1 本でも同じことができる**
（S-3 参照。テストで再現済み）。

**何と矛盾するか**

- 機能対応表「adminMint（裁量ミント）→ 削除／発行は mine() のみ」— 関数名は消えたが、
  同じ結果（任意額・任意宛先の発行）に到達する経路が残っている
- 提案書 §5.1「残高に触れる権限をゼロにする」、§5.6「他人の残高を増やせず・減らせず」
- 提案書 §5.5「実効的な発行上限 ≈ 237M」— この実装では**実効上限は cap の 300M**
- スキャナ観点でも `is_mintable` の説明が「固定スケジュールのみ」では成り立たない

**選択肢**

| | 内容 | 機能対応表との関係 |
|---|---|---|
| a | `setMiningReward` を「減額のみ・将来年のみ」に制限（`reward < 現在値` かつ `year > 現在年`）＋ `MiningRewardChanged` は既に実装済み | 行は維持したまま条件を追加（提案書 F-07）。**推奨** |
| b | 報酬表を `pure` 関数化し `setMiningReward` を削除 | 機能対応表「維持・変更」から「削除」へ移る＝要裁定（提案書 §5.2 の案） |
| c | 期間ごとの発行上限 `mintedInPeriod[年] <= 当年報酬 × 365` を機械強制 | 新規ガードの追加（提案書 F-23）。a と併用可 |

a だけでも「発行額を増やす方向の変更が不可能」になり、S-2 と併せて実効上限を ≈237M と
言い切れるようになる。

## S-2 [High] `mine(year)` の `year` は呼び出し側指定のまま — 逓減スケジュールがオンチェーンで強制されていない

**確認済み**: 2026 年に `mine(2022)` を 23 時間ごとに繰り返し、2022 年レート（10,000）で
発行し続けられた（3 回 = 30,000 SISC）。同一年の再採掘に回数制限も無い。

- MINER のホットキー（EC2）が漏れた場合の被害上限は **cap までの残枠全部**（10,000/23h のペース）
- 機能対応表は「mine / 報酬表 / poolAccount は維持」なのでこれは仕様通りだが、
  提案書 F-08 の指摘（監査・スキャナが問題視）はそのまま残る

**選択肢**: `year` 引数を廃止し `block.timestamp` から UTC 年を導出（提案書 F-08・§5.8 のスケッチ）。
これは機能対応表の「維持」を「変更」に変える裁定になる。暫定策として、MINER を Safe にする／
被害上限を S-1 の c（年間上限）で有界化する方法もある。

## S-3 [High] DEFAULT_ADMIN は固定だが、全ロールを自分に付与できる — かつ鍵の回転ができない

**確認済み**:

- `admin` は FREEZER / WHITELIST / MINING_ADMIN / MINER / RECORDER を自分に `grantRole` できた
  → ロール分離（「最上位権限から分離」）は **admin 鍵の強度以下**にしかならない
- `grantRole(DEFAULT_ADMIN_ROLE, <別アドレス>)` / 保持者に対する `revokeRole` / `renounceRole` は
  `AdminIsFixed` で revert。ただし**すべてが revert するわけではない**: 既に保持している
  `fixedAdminAccount` への再付与と、保持していないアドレスに対する revoke / renounce は
  `IAccessControl` の仕様どおり no-op で成功する（Safe のバッチを壊さないため）
  → **admin 鍵が漏れても永久に剥奪できない**。復旧手段は再デプロイ＋移行のみ

v3 では admin を別アドレスへ移せたので、「固定」はこの一点だけリスクを増やしている
（取引所要求 1 の「移行可能な admin」への懸念は消えるが、鍵の回転手段も消える）。

**結論（デプロイ制約）**: `roleHolders.admin` は **EOA にしてはいけない**。署名者を交換できる
Safe（提案書の推奨は Timelock 48h ＋ Safe 3-of-5）を入れること。アドレスは後から変更できないため、
デプロイ前に確定が必要。同様に、日常運用ロールは admin と別アドレス・別端末にする意味が
（S-3 の性質上）「admin 鍵が無事な限り」に限られることを対外説明でも曖昧にしない。

## S-4 [Medium] 凍結中も `approve` / `permit` が通る — 解凍と同時に引き抜かれる

**確認済み**: 凍結中の保有者が `permit` に署名 → allowance が立つ → `unfreeze` 後に
`transferFrom` で全額流出（同一ブロックでも可）。

`ERC20Restricted` は設計上 approve を制限しない（上流のコメントどおり）。v3.0 の NatSpec は
「凍結中は approve も制限される」と書いていたが実装はしていなかったため、v3.1 では
NatSpec を実装に合わせて修正済み（＝虚偽記載は解消）。ただしリスク自体は残る。

**対処**: 提案書 F-25 のとおり「unfreeze 前に対象アドレスの `Approval` ログを全件確認する」を
解凍手順書の必須ゲートにする。コードで塞ぐ場合は `_approve` の override（凍結中の増額のみ拒否）。

**裏返しのケースは 2026-09-17 に解消済み。** 「凍結された *spender* が、以前に得た allowance で
他人の残高を抜く」経路は `_spendAllowance` の override で塞いだ（テスト確認済み）。S-4 が残るのは
「凍結された *保有者* 自身の approve が、解凍後に行使される」方向のみ。
なお `approveAndCall`（ERC-1363）は凍結中でも成功するため、解凍前の `Approval` ログ確認は
`approveAndCall` 経由の承認も対象に含めること。

## S-5 [受容] `poolAccount` を凍結すると採掘が止まる（自傷 DoS・可逆）

**確認済み**:

- `freeze(poolAccount)` → `mine()` が `ERC20UserRestricted` で revert（unfreeze すれば復帰）
- `setPoolAccount` に制限状態のチェックが無いため、**凍結中のアドレスを受取先に設定**して
  採掘を止めることもできた

**一度コードで塞いだが、副作用が重く撤回した（2026-09-17）。**

constructor による `poolAccount` の自動登録と、`setPoolAccount` の「登録済み限定」要求は、
確かに S-5 を構造的に不可能にした。しかし ALLOWED は終端状態なので、**あらゆる発行先が永久に
凍結不能**になる。S-1（MINING_ADMIN + MINER で cap 残枠を任意アドレスへ発行できる）が「未修正で
許容」されていたのは、発行されても事後に `freeze` で封じ込められるからだった。自動登録はその
前提を壊し、**S-1 の被害を回復不能にしていた**（テストで再現済み: 1 億 SISC を受け取った
アドレスを誰も凍結できない）。

可逆な可用性障害（S-5、解凍すれば復旧）と、不可逆な封じ込め能力の喪失を比較し、後者を避けた。

**現在のガード**: `setPoolAccount` は BLOCKED のアドレスを拒否する（`PoolAccountIsFrozen`）。
「凍結中アドレスを受取先に設定して採掘を止める」経路は塞がれているが、設定後に pool を凍結
することは可能で、その場合 `mine()` は revert する。解凍すれば復旧する。

**運用の選択肢**: `registerExchange(poolAccount)` を実行すれば S-5 は起きなくなるが、その pool は
恒久的に凍結不能になる。トレードオフを理解したうえで判断すること（`v3.1-changes.md` §2-5）。

**この撤回が守る範囲（重要）**: 撤回で戻るのは「**新たな**凍結免除を作れないこと」であって、
「発行先を必ず凍結できること」ではない。

`setPoolAccount` は ALLOWED のアドレスを受け付けるため、登録済みの取引所アドレスが 1 件でも
存在すれば、**MINING_ADMIN_ROLE + MINER_ROLE の組**は `setPoolAccount(登録済み)` → `mine()` で
発行先を凍結免除アドレスにできる（実測で確認）。この場合の資金は取引所の管理下に入るため
攻撃者が自由に引き出せるわけではないが、**凍結による封じ込めはできない**。
したがって確実に凍結できるのは「未登録アドレスを発行先にした場合」に限られる。
両者は `registerExchange` を呼べないので、新しいアドレスに凍結免除を与えることはできない。一方 **admin 鍵には効かない**: `DEFAULT_ADMIN_ROLE` は自分に
`WHITELIST_ROLE` を付与し、任意アドレスを登録してから pool に設定できる（S-3）。実測で
99,000,000 SISC を受け取ったアドレスが `ExchangeAddressProtected` により永久に凍結不能に
なることを確認している。admin 鍵が漏れた時点でトークンは失われるという S-3 の前提は変わらない。

## S-6 [解消] 取引所アドレスの保護が `WHITELIST_ROLE` 鍵 1 本で即時に外せた

**2026-09-16 のホワイトリスト追記専用化で構造的に解消。** `unregisterExchange` を削除し、
`_setRestriction` で `ALLOWED` を終端状態にしたため、登録済みアドレスの保護を外す経路が
コード上に存在しない。`DEFAULT_ADMIN_ROLE` が `FREEZER_ROLE` と `WHITELIST_ROLE` を自分に
付与しても `freeze` は `ExchangeAddressProtected` で revert する。`unfreeze` は revert では
なく**状態を変えない no-op** で成功し、ALLOWED は維持される（冪等化後の挙動。S-10）。
いずれもテストで確認済み。

ただし**不可逆性そのものが新しいリスク**として残る。

- 誤登録の訂正手段が再デプロイしか無い
- `WHITELIST_ROLE` 鍵が漏れた場合、任意アドレスに**恒久的な**凍結免除を与えられる
  （件数・レート制限は未実装。提案書 §5.4 のローリング 7 日 200 件は引き続き未実装）

**対処**: `WHITELIST_ROLE` を Safe にし、登録前のアドレス確認手順を書面化する。取引所への
説明は「登録後は解除できない」に変わるため、S-7 と併せて合意内容を更新すること。

## S-7 [Low] 取引所のユーザー毎入金アドレスは事前登録できない

動的生成されるため、登録対象はホット・コールド・出金元・スイープ先に限られる。
LBank 要求 3 を「全入出金アドレスの除外」と読むと**技術的に充足不能**。提案書 §5.4 と同じ結論で、
実装側で解決できる問題ではないので書面で合意する。

## S-8 [Low] 凍結に期限が無い（機能対応表どおり）

FREEZER 鍵を失うと恒久凍結になる。`unfreeze` は FREEZER 専用で、admin は自分に FREEZER を
付与すれば解除できる（＝ admin 鍵が最後の砦）。提案書の自動失効（7 日／30 日）は未実装。
また freeze はメモリプールで観測できるため、対象は先回りして送金できる（v3.0 と同じ）。

## S-9 [Low] v3.0 との ABI 互換性が切れる箇所

- `initialSupply()` は廃止（`genesisSupply()` に改名）
- `maxSupply()` は `cap()` のエイリアスとして残置（互換）
- `POOLER_ROLE()` / `PAUSER_ROLE()` / `pause()` / `adminMint()` 等は消滅
- `unregisterExchange()` は消滅（ホワイトリストの追記専用化。S-6）
- カスタムエラーに `ExchangeRegistrationIsPermanent` / `IndexOutOfBounds` が追加。
  `NotRegistered` は消滅
- getter に `registeredExchangeCount()` / `registeredExchangeAt(uint256)` /
  `getRegisteredExchanges()` / `legacyMinedSupply()` / `minedByThisContract()` が追加
- カスタムエラーにさらに `DuplicateGenesisHolder` / `PoolAccountIsFrozen` /
  `InvalidExchangeAddress` / `NoRewardForYear` が追加
- `AlreadyRegistered` / `AlreadyFrozen` / `NotFrozen` は**削除**。空振り呼び出しは revert せず
  冪等な no-op になった（下記 S-10）
- `supportsInterface(0x84b0196e)`（IERC5267）が `false` → `true` に変化
- **`isRegisteredExchange(address)` は `isWhitelisted(address)` に改名**（外部レビュー F-02）。
  旧名は ABI に存在しないため、先行して連携準備をしている場合は差し替えが必要
- **挙動の非互換**: `setPoolAccount` は凍結中アドレスと `address(this)` を拒否し、凍結検査を
  同値 no-op より先に行う（成功＝pool が現在使える宛先、が常に成り立つ）。`unfreeze` に
  ゼロアドレス検査を追加。
  `mine()` の報酬ゼロは `InvalidNumber` → `NoRewardForYear` に変化。
  `setMiningReward` / `setPoolAccount` / `freeze` / `unfreeze` / `registerExchange` の空振りは
  revert せず冪等な no-op になった（S-10）
- `ExchangeRegistered` のシグネチャが `(address indexed, bool)` から
  `(address indexed, uint256 index)` に変更（解除が無くなり bool が無意味になったため）
- ロール定数は `private` → `public` に変更（ABI に出る）

`scripts/` と運用ツール（readcheck の immutable マスク等）は要修正。
`artifacts/` は v3.0 の Remix 出力のまま残っており、削除済みの `adminMint` / `adminBurn` /
`burn` / `burnFrom` / `pause` を含む ABI を配布する状態だったため、**リポジトリから削除し**
`solc-input.json`（standard-json input）に一本化した。ビルド・検証はそちらを正本とする。
なお `scripts/ethers-lib.ts` / `scripts/web3-lib.ts` は `browser/artifacts/<name>.json` を
読む Remix 雛形のままなので、この削除により参照先を失う（元々 `Storage` をデプロイする
雛形で本コントラクトとは無関係）。

## S-10 [Low] イベントが二重に出る（実体のない emit は解消済み）

`freeze` は `AccountFrozen` と `UserRestrictionsUpdated`、`registerExchange` は
`ExchangeRegistered` と `UserRestrictionsUpdated` の 2 本を出す（`ERC20Restricted` 由来）。
監視側で二重カウントしないこと。`registerExchange` の 2 本はいずれも 1 アドレスにつき最大 1 回で、
解除側のイベントは存在しない。

なお「状態が変わっていないのにイベントだけ出る」問題は**全セッターで解消した**。ただし
空振りを revert させるのではなく、**冪等な no-op** として実装している。`freeze` / `unfreeze` /
`registerExchange` / `setPoolAccount` / `setMiningReward` は、既に目的の状態であれば成功して
何もせず、イベントも出さない。

当初は空振りを `AlreadyFrozen` / `NotFrozen` / `AlreadyRegistered` / `ValueUnchanged` で
revert させていたが、これを撤回した。`freeze` はメンプールで可視（S-8）なため、Safe から
N 件をまとめて凍結する最中に監視ボットや共同署名者が 1 件を先に凍結すると、**バッチ全体が
巻き戻り残りが凍結されない**ことがテストで再現された。インシデント対応の経路で可用性を
下げるため、冪等に改めた（4 つのエラーは ABI から削除済み）。

結果として `AccountFrozen` / `ExchangeRegistered` / `MiningRewardChanged` / `PoolAccountChanged`
は**必ず実際の状態遷移を伴う**。監視側は「イベント＝状態変化」と仮定してよい。テストで確認済み。

**残っている中断要因**: 冪等化が解くのは「既にその状態だった」場合だけである。`freeze` を
**登録済み（ALLOWED）アドレス**に対して呼ぶと従来どおり `ExchangeAddressProtected` で revert し、
Safe のバッチは中断する。しかも再試行では直らず、そのアドレスを外してバッチを組み直すしかない。
インシデント時に登録簿を確認している余裕は無いことが多いので、**一括凍結の前に
`isWhitelisted` でスクリーニングする**ことを手順に入れること。

別件として挙げていた「`genesisHolders` の重複アドレスを検証していない」点は、constructor に
`DuplicateGenesisHolder` の検査を追加して**解消済み**（`v3.1-changes.md` §1）。

## S-11 [Medium] 23 時間間隔のため「年 365 回」ではなく「年 381 回」発行される（未修正）

**確認済み**: `lastMinedAt` は固定アンカーではなく前回実行時刻からの相対なので間隔がスライドし、
365 日に `365 × 24 ÷ 23 = 380.87` → **381 回**の `mine()` が収まる。報酬表は年額の計画だが、
1 年あたりの支払回数は拘束されていない。正直な採掘者でも年 **+4.4%** 多く発行される
（報酬表の全出力: 365 回なら 40,148,922 SISC、381 回なら 41,908,875 SISC）。

**未修正の理由**: 回数制限や固定アンカーの導入はトークノミクスの変更であり、別途裁定が必要。
現状は README と本書に明記するに留めた。なお計画の全出力（≤41.9M）はデプロイ直後の残枠
87,732,080 を下回るため、**正直な採掘だけでは cap に到達しない**（約 45.8M が採掘では未到達）。

## S-12 [Low] `multiTransfer` は全件失敗型（未修正・仕様）

**確認済み**: 100 件のバッチ中 1 件の宛先が凍結されていると、`_update` が revert して
**バッチ全体がロールバック**する。部分成功モードは無い。

**未修正の理由**: スキップ方式にすると「送ったつもりで届いていない」silent failure を生むため、
全件失敗のほうが安全。取引所側は `canTransact()` / `isFrozen()` で事前スクリーニングするか、
バッチを小さく分割すること。README に明記した。

## S-13 [Medium] constructor の struct は取り違えを防がない（コードでは防止不能）

**確認済み**: `InitialRoleHolders` は同型の `address` 6 語として ABI エンコードされ、位置引数と
区別がつかない。`admin` と `miner` を入れ替えてデプロイしても検査を通過し、
**`fixedAdminAccount` がホットな miner 鍵になって回復不能**になる（`grantRole` /
`revokeRole` / `renounceRole` がすべて `AdminIsFixed`）。`freezer` ↔ `whitelistAdmin` の
取り違えは admin が修復できるため、致命的なのは `admin` スロットのみ。

**対処**: コードでは検出不能なので、ツールで緩和した。`scripts/deploy-sisc.ts` は名前付き
オブジェクトで呼び出し、ゼロアドレス・重複・合計額・gasLimit を事前検証する。
`scripts/verify-deployment.ts` はデプロイ直後に `getRoleMembers()` と設定を突合する。
**Remix / Etherscan から直接デプロイしないこと。** 虚偽だった NatSpec の記述も修正済み。

## S-14 [Low] ホワイトリスト登録簿は無制限に増え、縮小できない

**確認済み**: `getRegisteredExchanges()` は約 2,510 gas/件で線形に増加し、**約 11,900 件**で
30M の `eth_call` 上限を超える。登録は恒久なので縮小手段が無く、`WHITELIST_ROLE` 鍵が漏れた
場合は一括取得を永久に劣化させられる。`registeredExchangeAt()` によるページングは常に可能。
現実の登録対象（取引所のホット・コールド・出金元・スイープ先）は多くても数百件なので、
通常運用では 3 桁の余裕がある。S-6 の残存リスク（件数・レート制限が無い）と同根。

## S-15 [Info] Cancun 完備の EVM が必須（理由は 2 つ）

**確認済み**（バイトコードを PUSH 即値考慮で走査）: `TSTORE` ×1・`TLOAD` ×1（EIP-1153、
`ReentrancyGuardTransient` 由来）に加えて **`MCOPY` ×2（EIP-5656）** が含まれる。`MCOPY` は
solc が evmVersion cancun 以降で自動生成するもので、再入ガードとは無関係。

つまり **`ReentrancyGuardTransient` を外しても Cancun 未満のチェーンには出せない**
（evmVersion を下げる必要があり、バイトコードが変わって検証入力も作り直しになる）。
prague / osaka 固有オペコードは含まれないため、実際の下限は Cancun。デプロイ先チェーンが
EIP-1153 と EIP-5656 の両方を備えることを、listing 前に必ず確認すること。

## 良くなった点（監査で加点になる）

- **バーン経路が 1 つも無い**ため、`ERC20Capped` の cap が実質的に**累積発行上限**として機能する
  （`transfer(0x0)` も `ERC20InvalidReceiver` で revert。提案書 F-16 の「burn → re-mint で上限を
  無効化」は構造的に解消）
- `multiTransfer` は permissionless だが、他人の残高には触れない（`ERC20InsufficientBalance` で
  revert することを確認済み）。権限一覧を 1 つ減らせる
- ホワイトリストは**追記専用**で、登録済み取引所アドレスは `DEFAULT_ADMIN_ROLE` を含むどの鍵でも
  凍結・解除できない（`unfreeze` 経由の迂回路も塞いだ）。保護が鍵の管理状態に依存しなくなった
- 登録簿が `getRegisteredExchanges()` で全件列挙でき、取引所側が自分のアドレスの登録状態を
  第三者に依存せず検証できる
- ロール保持者が `getRoleMembers` でオンチェーン列挙可能、凍結・登録状態も view で検証可能
