## 1. 機能対応表との対応

### 削除した機能

| 機能対応表の行 | 実装 |
|---|---|
| burn / burnFrom（本人バーン） | `ERC20Burnable` を継承しない。`burn` / `burnFrom` は ABI に存在しない |
| adminBurn | 削除。管理者が他人の残高を没収する関数は存在しない（承認済みの `transferFrom` は保有者の承認に基づくため別） |
| adminMint | 削除。発行経路は `mine()` のみ。移行時の供給は constructor で一度だけ mint |
| pause / unpause | `ERC20Pausable` を継承しない。`pause` / `unpause` / `paused` は ABI に存在しない。`PAUSER_ROLE` も削除 |
| 最上位権限（DEFAULT_ADMIN）の移行 | `_grantRole` / `_revokeRole` を override。`DEFAULT_ADMIN_ROLE` は constructor で `fixedAdminAccount` に固定し、他アドレスへの付与・剥奪・放棄（`renounceRole`）はすべて `AdminIsFixed` で revert |

### 維持・変更した機能

| 機能対応表の行 | 実装 |
|---|---|
| freeze / unfreeze（アドレス単位・時間制限なし） | `ERC20Restricted` の `BLOCKED`。`freeze()` / `unfreeze()` は `FREEZER_ROLE`。期限なし（v3.0 と同じ） |
| ホワイトリスト（登録済みは凍結不能） | `ERC20Restricted` の `ALLOWED` ＋ 独自ガード（§2）。`registerExchange()` は `WHITELIST_ROLE`。**追記専用**で解除関数は無い。登録簿は `getRegisteredExchanges()` 等で全件列挙可 |
| grantRole / revokeRole / hasRole | `AccessControlEnumerable`（`getRoleMembers` / `getRoleMemberCount` / `getRoleMember` で保持者を列挙可）。ロール定数は `public` |
| setPoolAccount / setMiningReward | `MINING_ADMIN_ROLE`（最上位権限から分離）。`setMiningReward` に `MiningRewardChanged` イベントを追加 |
| mine / getMiningReward / 報酬表 / poolAccount | v3.0 と同じ。`mine(uint256 year)`・23 時間間隔・報酬表は constructor で 100 年分を設定 |

### 変更なしの標準部分

| 機能対応表の行 | 実装 |
|---|---|
| ERC-20 基本 | `ERC20` |
| 最大供給 3 億 | `ERC20Capped`。`MAX_SUPPLY` 定数（300,000,000 × 10^18）を constructor で渡す。v3.0 互換の `maxSupply()` は `cap()` のエイリアス |
| permit | `ERC20Permit` |
| transferAndCall | `ERC1363` |
| multiTransfer | 独自。`POOLER_ROLE` は廃止し permissionless（送信者自身の残高しか動かないため権限ではない）。1〜100 件 |
| storeWeb3MakerAIData | 独自（`RECORDER_ROLE`）。変更なし |
| 再入防止 | `ReentrancyGuardTransient`（`mine` / `multiTransfer`） |
| supportsInterface | `AccessControlEnumerable` / `ERC1363` |

### 機能対応表に無い付随変更

- `require(string)` を全廃し custom error に統一（revert データのみの変更。提案書 F-33）
- getter 追加: `isFrozen()` / `isWhitelisted()` / `getPoolAccount()`（凍結・登録状態を
  オンチェーンで検証可能にする。提案書 F-12）。さらにホワイトリストの追記専用化に伴い
  `registeredExchangeCount()` / `registeredExchangeAt(uint256)` / `getRegisteredExchanges()` を追加し、
  登録簿を全件オンチェーン列挙できるようにした（§2-3）
- `initialSupply`（immutable）は `genesisSupply` に改名。意味が「固定値」から
  「constructor で mint した実供給」に変わったため
- `freeze` / `unfreeze` / `registerExchange` / `setPoolAccount` / `setMiningReward` を**冪等**に
  した。既に目的の状態なら成功して何もせず、イベントも出さない（従来は状態変化が無くても
  イベントだけ emit していた）。revert にしなかったのは、Safe から N 件をまとめて凍結する
  最中に 1 件が先に凍結されるとバッチ全体が巻き戻るため（security-notes S-10）
- `setPoolAccount` に `address(this)` ガードを追加し、凍結検査を同値 no-op より**前**に移した。
  「成功＝pool が現在使える宛先である」が常に成り立つようにするため
- `unfreeze` にゼロアドレス検査を追加（`freeze` と対称に）
- `_spendAllowance` を override し、**凍結アドレスが他人の allowance を使えない**ようにした。
  上流 `ERC20Restricted` は `from` / `to` しか見ないため、凍結した攻撃者が
  `transferFrom(被害者, 清潔なアドレス, ...)` で資金を抜けてしまっていた（`approve` /
  `permit` は従来どおり無制限＝ S-4）
- `setPoolAccount` は凍結中アドレスと `address(this)` を拒否する。`poolAccount` の自動登録は
  一度実装したのち撤回した（理由は §2-5）
- constructor が `genesisHolders` の**重複を拒否**（`DuplicateGenesisHolder`）
- `legacyMinedSupply` を immutable として保存・公開し、`minedByThisContract()` を追加。
  併せて上限判定を「genesis 合計以下」から「cap 以下」に修正（§3）
- `mine()` の報酬ゼロを `NoRewardForYear` として `InvalidNumber` と区別
- `registerExchange` がコントラクト自身を拒否（`InvalidExchangeAddress`）
- `_revokeRole` を「実際に保持している場合のみ revert」に変更。未保持アドレスへの
  `renounceRole(DEFAULT_ADMIN_ROLE, ...)` が Safe のバッチを巻き添えにしなくなった
- `supportsInterface` が `IERC5267`（`eip712Domain()`）を申告
- ホワイトリストの照会 getter を `isRegisteredExchange` から **`isWhitelisted` に改名**した。
  取引所へ提示した部品表の用語に合わせるため（外部レビュー F-02）。書き込み側は
  `registerExchange`、イベントは `ExchangeRegistered` のままで、いずれも {ERC20Restricted} の
  同じ ALLOWED 状態を指す
- `_update` で `to == address(this)` を `ERC20InvalidReceiver` で拒否。トークン契約自身へ
  送られた分は burn も rescue も無く永久に失われ cap も消費するため、通常送金を含む全経路で
  塞いだ。専用エラーではなく OZ 標準の `ERC20InvalidReceiver` を使うので、統合側からは
  `transfer(address(0))` と同じ失敗に見える（外部レビュー F-08）
- `scripts/build.sh` を solc CLI のパースから **node API 呼び出し**に変更。CLI は SMT ソルバが
  無い環境で `>>> Cannot retry compilation with SMT ...` を標準出力に混ぜるため、z3 等が入って
  いない監査・取引所・CI の環境では `npm run build` と `npm test` が失敗していた（外部レビュー F-01）
- `scripts/deploy-sisc.ts` に `estimateGas` の併用と、`legacyMinedSupply` の負値・chainId の
  安全整数・genesis 各件の cap 超過の検査を追加（外部レビュー Q13 T-1 / F-09）

## 2. ホワイトリストの独自ガードと追記専用化

### 2-1. 要件

1. ホワイトリスト機能が実装されていること
2. 登録アドレスがオンチェーンで検証可能であること
3. **一度追加されたアドレスは削除・更新できないこと**
4. 登録アドレスは凍結対象にならないこと

### 2-2. 実装

`ERC20Restricted` 単体には遷移規則が無く、`_blockUser` / `_resetUser` は現在の状態を見ずに
書き換える。状態を書く経路は `_setRestriction` の 1 か所なので、そこを override して
**`ALLOWED` を終端状態**にした。

```solidity
function _setRestriction(address account, Restriction next) internal override {
    Restriction current = getRestriction(account);
    if (current == Restriction.ALLOWED) {
        if (next == Restriction.BLOCKED) revert ExchangeAddressProtected(account);
        revert ExchangeRegistrationIsPermanent(account);
    }
    if (current == Restriction.BLOCKED && next == Restriction.ALLOWED) {
        revert FrozenAddressCannotBeRegistered(account);
    }
    super._setRestriction(account, next);
}
```

| # | 禁止する遷移 | 目的 | revert |
|---|---|---|---|
| 1 | `ALLOWED` → `BLOCKED` | 登録済みアドレスへの freeze を不可にする（要件 4） | `ExchangeAddressProtected(account)` |
| 2 | `ALLOWED` → `DEFAULT` | 登録の解除を不可にする（要件 3） | `ExchangeRegistrationIsPermanent(account)` |
| 3 | `BLOCKED` → `ALLOWED` | 凍結中アドレスの登録＝実質的な凍結解除を防ぐ | `FrozenAddressCannotBeRegistered(account)` |

`unregisterExchange()` は **削除した**。ABI に存在しないため、`DEFAULT_ADMIN_ROLE` を含む
どのロールからも登録を外せない。2 の検査は「解除関数が無い」ことの構造的な裏付けであり、
将来 `_resetUser` を呼ぶコードが増えても `ALLOWED` は剥がれない。

| 関数 | ロール | 事前条件 | 遷移 |
|---|---|---|---|
| `freeze(a)` | FREEZER | `a != 0`、`a` が `ALLOWED` でない | `DEFAULT` → `BLOCKED` |
| `unfreeze(a)` | FREEZER | `getRestriction(a) == BLOCKED` | `BLOCKED` → `DEFAULT` |
| `registerExchange(a)` | WHITELIST | `a != 0`、`a` が `ALLOWED` でない、`a` が `BLOCKED` でない | `DEFAULT` → `ALLOWED`（終端） |

`registerExchange` は登録済みアドレスに対しては何もせず正常終了する（冪等）。上書きも
登録簿（2-3）への重複追加も起こらない。

### 2-3. オンチェーン検証（要件 2）

`getRestriction()` で 1 件ずつ確認できるほか、追記専用の配列 `_registeredExchanges` に
登録順で追加され、全件を列挙できる。

| 関数 | 用途 |
|---|---|
| `isWhitelisted(address) -> bool` | 単一アドレスの登録有無 |
| `registeredExchangeCount() -> uint256` | 登録件数（減少しない） |
| `registeredExchangeAt(uint256) -> address` | 登録順のインデックス参照（範囲外は `IndexOutOfBounds`） |
| `getRegisteredExchanges() -> address[]` | 全件を 1 回の `eth_call` で取得 |

イベントは `ExchangeRegistered(address indexed account, uint256 index)`。1 アドレスにつき
最大 1 回しか emit されず、解除イベントは存在しない。

### 2-4. 不可逆性の代償（運用上の注意）

- **誤登録は取り消せない。** 間違ったアドレスを登録した場合、修正手段は再デプロイのみ。
  `registerExchange` の実行前確認を手順として必須化すること。
- **`WHITELIST_ROLE` 鍵が漏れると、任意アドレスに恒久的な凍結免除を与えられる。**
  件数・レート制限は未実装で、付与済みの登録は admin でも取り消せないため被害は恒久的に残る。
  `WHITELIST_ROLE` は Safe にすること。
- 取引所への説明は「登録済みアドレスは凍結されない」に加えて **「登録は解除できない」** に変わる。

`canTransact()` は上流の既定（ブロックリスト）のまま。`ALLOWED` は一般利用者の取引ゲートでは
なく、**freeze できないことの印**でしかない。したがって `ALLOWED` 登録は誰の送受信も新たに
制限しない。


### 2-5. poolAccount はホワイトリストに自動登録しない（重要な設計判断）

一度は constructor で `poolAccount` を自動登録し、`setPoolAccount` に「登録済みであること」を
要求する実装にした。S-5（pool を凍結すると採掘が止まる自傷 DoS）をコードで塞ぐためだったが、
**副作用のほうが重かったため撤回した。**

| | 自動登録する実装 | 現在の実装 |
|---|---|---|
| S-5（pool 凍結で採掘停止） | 構造的に不可能 | 起きうる。ただし**解凍すれば復旧する可逆な障害** |
| 発行先の凍結 | **永久に不可能** | 可能 |
| S-1 で不正発行された場合 | 受取先を凍結できず封じ込め不能 | 受取先を凍結して資産を止められる |

`setPoolAccount` は `MINING_ADMIN_ROLE` が任意のアドレスを指定でき、`setMiningReward` に上限も
無い（S-1）。自動登録はその**発行先を常に凍結免除**にしてしまい、S-1 が「未修正で許容」されて
いた前提――事後に運用で封じ込められること――を壊していた。可逆な可用性障害（S-5）と、
不可逆な封じ込め能力の喪失を比べ、後者を避ける判断をした。

現在の `setPoolAccount` のガードは「**BLOCKED でないこと**」（`PoolAccountIsFrozen`）のみ。
凍結中アドレスを受取先に設定して採掘を止める経路は塞ぎつつ、スナップショット検査なので
設定後に凍結されることは防がない。それが意図した可逆な失敗モードである。

`poolAccount` をホワイトリスト登録するかは**運用の選択肢**として残っている。登録すれば S-5 は
起きなくなるが、その pool は恒久的に凍結不能になる。トレードオフを理解したうえで決めること。

## 3. constructor（引数化）

`adminMint` を削除したため、移行時の実供給と各ロールの初期保持アドレスは constructor でしか
与えられない。**ここを間違えるとデプロイ後に修正できず再デプロイになる。**

```solidity
struct InitialRoleHolders {
    address admin;          // DEFAULT_ADMIN_ROLE（デプロイ時に固定・以後変更不能）
    address freezer;        // FREEZER_ROLE
    address whitelistAdmin; // WHITELIST_ROLE
    address miningAdmin;    // MINING_ADMIN_ROLE
    address miner;          // MINER_ROLE
    address recorder;       // RECORDER_ROLE（0 なら保持者なし）
}

constructor(
    InitialRoleHolders memory roleHolders,
    address poolAccount_,
    address[] memory genesisHolders,
    uint256[] memory genesisAmounts,
    uint256 legacyMinedSupply
)
```

6 アドレスは可読性のため struct で受けているが、**取り違えは防げない**。同型の `address` が
6 語並ぶだけで、ABI レベルでは位置引数と区別がつかない。フィールド名が生きるのは
名前付きオブジェクトから呼び出す場合だけで、Remix は tuple を 1 つのテキスト欄、
Etherscan は生の hex で受ける。

**`admin` スロットの誤りは回復不能**（`fixedAdminAccount` になり、付与・剥奪・放棄が
すべて `AdminIsFixed`）。したがってデプロイは `scripts/deploy-sisc.ts`（名前付き
オブジェクト＋事前チェック）で行い、直後に `scripts/verify-deployment.ts` で
`getRoleMembers()` と突合すること。

| 引数 | 内容 | 検証 |
|---|---|---|
| `roleHolders` | 各ロールの初期保持アドレス | `recorder` 以外はゼロアドレス不可。デプロイヤーへの**自動付与は無い**（初期保持者にデプロイヤーを指定すること自体は禁止していない） |
| `poolAccount_` | 採掘報酬の受取先 | ゼロアドレス不可 |
| `genesisHolders` / `genesisAmounts` | 移行時点の実供給の配り先と金額（wei） | 1〜100 件・長さ一致・各アドレス非ゼロ・**重複不可**・各金額 > 0・合計は 3 億以下 |
| `legacyMinedSupply_` | 旧版までの既採掘実績（wei、`totalMiningSupply` の初期値） | mint はしない会計値。**累積**値なので残存供給を超えてよく、上限は cap のみ |

`GenesisSupplyMinted(genesisSupply, legacyMinedSupply)` を 1 回だけ emit する。

### デプロイ前に確定すべき値（コード側では決められない）

1. **移行時点の実供給**: 旧版の採掘を停止した時点の `totalSupply()`。スナップショットと
   交換債務を突合して確定する（提案書 §5.5・F-15）
2. **genesis の配り先**: 単一アドレス 100% 保有を避けるかどうか（提案書 裁定 D8）
3. **既採掘実績** `legacyMinedSupply`
4. **6 ロールのアドレス**: Safe か EOA か。`admin` は後から変更できない
5. **`poolAccount_`**

### デプロイ直後に実行する運用手順

**順序が重要**: 不可逆な操作の前に、必ず検証を先に行う。

1. `CONTRACT=0x... RPC_URL=... npx ts-node scripts/verify-deployment.ts` を実行し、6 ロールの保持者・
   供給会計・genesis 配分・poolAccount の登録状態を設定ファイルと突合する。
   ここで 1 件でも不一致があれば**それ以上何もせず再デプロイを検討する**
2. 取引所から申告されたアドレス（ホット・コールド・出金元・スイープ先）を
   `registerExchange` で登録する。**登録は取り消せない**ので 1 件ずつ確認しながら行う

`poolAccount` は自動登録されない。登録するかどうかは §2-5 のトレードオフを読んで判断すること。
引数例（ethers v6）:

```js
const roleHolders = {
  admin: "0x...",          // 変更不能
  freezer: "0x...",
  whitelistAdmin: "0x...",
  miningAdmin: "0x...",
  miner: "0x...",
  recorder: "0x...",       // 不要なら ethers.ZeroAddress
};
await factory.deploy(
  roleHolders,
  "0x...",                                  // poolAccount
  ["0x...", "0x..."],                        // genesisHolders
  [200_000_000n * 10n ** 18n, 12_267_920n * 10n ** 18n], // genesisAmounts（実供給に合わせる）
  9_690_500n * 10n ** 18n                    // legacyMinedSupply
);
```

## 6. 検証

テストは `test/shirushicoin.test.js` としてリポジトリに同梱した（`npm test`）。`scripts/build.sh`
が `solc-input.json` から生成した成果物に対して実行されるため、**エクスプローラで検証するのと
同じバイトコード**を検証している。同梱スイート（`test/shirushicoin.test.js`・check 101 件）が実際に検査しているのは次のとおり。

| 群 | 内容 |
|---|---|

### 検証の網羅について

外部レビュー（2026-09-17）で「スイートに無い」と指摘された 8 項目は群 11 に、こちらで
未カバーとして残していた 4 項目は群 12 に取り込み、**現時点で把握している未検証経路は無い**。

群 12 の ERC-1363 受信コントラクトは、テスト実行時に solc-js でソースからコンパイルして

## 7. ビルドとデプロイのツール

`adminMint` も burn も無く `DEFAULT_ADMIN_ROLE` も移せないため、**`admin` / `genesisHolders` /
`genesisAmounts` / `legacyMinedSupply` は後から変更できない**（`poolAccount` は `setPoolAccount`、
運用ロールは `grantRole` / `revokeRole` で変更できる）。Remix / Etherscan からの直接デプロイでは tuple が 1 つのテキスト欄や生 hex に
なり、取り違えが検出できない（S-13）。そのため専用のツールを用意した。

```
npm install
npm run build                 # solc-input.json -> build/ShirushiCoin.json
cp scripts/sisc.config.example.ts scripts/sisc.config.ts   # 記入する
npm run deploy                # ドライラン（事前チェックのみ、tx は送らない）
CONFIRM=DEPLOY RPC_URL=... PRIVATE_KEY=... npm run deploy
CONTRACT=0x... RPC_URL=... npm run verify                  # デプロイ直後に必ず最初に実行
```

### `scripts/build.sh`

`solc-input.json` を唯一の正本として `{ abi, bytecode, deployedBytecode, immutableReferences,
solcInputHash }` を生成する。`deployedBytecode` と `immutableReferences` は検証で、
`solcInputHash` は成果物の鮮度確認で使う（`build/` は gitignore なので古い可能性があるため）。

### `scripts/deploy-sisc.ts`

名前付きオブジェクトで constructor を呼ぶ（フィールド名が生きる唯一の形）。事前チェック:

| 検査 | 目的 |
|---|---|
| ゼロアドレス・長さ一致・genesis 重複・合計 ≤ cap | constructor と同じ条件を送信前に落とす |
| **gasLimit を genesisHolders 件数に連動**（実測 7,919,946〜11,512,077 に 15% 余裕） | 一律下限だと 100 件でチェックを通過して実行時に失敗し、ガスを焼く |
| **chainId の照合** | 最初のネットワーク接触が不可逆な tx にならないようにする |
| **生成予定アドレスとの衝突検出** | `poolAccount` / `genesisHolders` がトークン自身だと永久ロック（L-1） |
| 成果物と `solc-input.json` のハッシュ一致 | 古い `build/` でのデプロイを防ぐ |
| `admin` と運用ロールの同一指定を個別に警告 | `admin` の取り違えのみ回復不能 |

### `scripts/verify-deployment.ts`

デプロイ直後、**他の操作より先に**実行する。読み取り専用。

| 検査 | 内容 |
|---|---|
| **デプロイ済みコードの照合** | `eth_getCode` とビルド結果を、メタデータ末尾と immutable 領域をマスクして比較する。「監査した通りのコードがこのアドレスにあるか」に答える唯一の検査。コードが存在しないアドレスを指定した場合はその場で打ち切る |
| **削除済み機能の不在** | チェーン上の runtime コードをセレクタで走査する。**ただしバイトコード照合が一致したときだけ実行する。** セレクタの不在は「そのランタイムの dispatch table に無い」ことしか示さず、proxy では 7 件すべてが不在に見えて委譲先に実装が存在しうることを実測で確認したため。不一致時はスキップし、その理由を表示する |
| **EIP-712 ドメイン** | `eip712Domain()` と `DOMAIN_SEPARATOR()` を検証する。ドメインは immutable としてコードに焼かれるため、上のバイトコード照合ではマスクされて比較対象外になる（`permit` が想定どおり動くかはここでしか分からない） |
| chainId / 成果物の鮮度 | 上と同じ |
| ロール・供給会計・genesis 配分・pool | 設定ファイルと突合 |

**限界（明記しておく）**: このスクリプトは deploy と同じ `sisc.config.ts` を読むため、
証明できるのは「チェーンが設定どおりであること」であって「設定が正しいこと」ではない。
**設定ファイル自体が取り違っている場合はすべて通過する。** そのためロールのアドレスは全文を
出力する。必ず別の担当者が独立した資料と読み合わせること。
